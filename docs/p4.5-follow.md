# P4.5 关注模块（第一步：只读建议）

> 状态：第一步完成；写关注还没接。

## 做了什么

- vendor MCP 新增两个工具：
  - `bili_followings`：只读当前账号关注列表（mp 边界：最多 5 页，每页 50）；
  - `bili_follow`：关注/取关（写操作，只有白名单里带它时才能调用，目前默认不放进白名单）。
- `bili_search` 返回值新增 `mid`，后续队列条目会带 UP 的 UID。
- `src/watch/suggestions.js`：把队列里已收/待判的视频按 UP 聚合，用判据方向打分，排除已关注的 UP，产出 3–5 条建议，存 `watch/suggestions.json`。
- 悬浮球面板顶部加两个标签：「待判」「关注建议」；没有待判时点球直接进「关注建议」；每行显示 UP 名 + 推荐理由 + 代表视频；底部「刷新建议」。
- 面板 accept 也接了自动补深读（用户不需要多点一步）。

## 2026-11-10 追加（P4.5 收尾）

> **2026-11-11 产品决定：放弃 `agent` 档，面板只保留 `off / code`。** 以下 agent 相关记录仅留档；`WATCH_MODES` 不再接受 `agent`，旧配置自动迁移为 `code`。

- **评论条数滑块**：`mentionPerDay` 范围放宽到 0–10，默认 3；放在喂养页“保存喂养参数”的第四个滑块。
- **下轮优先**：每轮先读关注列表（最多 10 个 UP），每人拉最近 5 条，预留 1 个名额并 +6 分；读不到关注列表就退回纯关键词。
- **自我循环修复**：`bili_followings` 返回 `self_mid`，轮次/建议都排除自己的账号；实测中误进队列的两条自己的视频已按“自己的账号，跳过”清掉。
- **2026-11-10 的旧 spike**：`watch_run action=agent_probe` 只创建临时会话；当时 `deepseek-account/deepseek-flash` 全部 `TRANSPORT`，不能据此判定所有 agent 路径不可用。
- **2026-11-11 探针复核**：旧 `minimal` 探针在 `kimi-code-cn/k3.1-pro` 回复“收到”、turn completed，但请求实际带 83 个继承工具，因此只证明文本会话，不满足只读验收。
- **正式 agent 档已实现**：新增 `watch-duty` preset；创建时先 `restrict({allow:[]})`，再只注册 `watch_bili_followings/search/user_videos/subtitle` 四个有界只读工具。候选 BV/元数据必须来自实际工具结果，深读必须有实际非空字幕；核心记忆钩子跳过 `watch-agent-*` / `watch-probe-*`。
- **同一产物契约**：复用 `writeRoundReport` / `buildQueue` / `recordUsage`；手动和定时跑统一分流。创建、模型、解析失败可显式降级 code；取消、预算耗尽、提交阶段 I/O 错误不重跑。真实 usage 优先取 provider，失败轮次也记实测部分用量。
- **探针验收**：必须是 watch-duty、turn/end=completed、回复“收到”、可见工具数 0；`watch_run agent_probe` 可临时指定 provider/model 复测旧路由，不修改部署默认。
- **离线验证：139/139，语法检查 42 个 JS 文件。** 当前源码修改尚未被运行中的 Host 导入；完整重启后仍需做严格探针和一次真实 agent 跑轮，验收前不宣称正式可用。详见 [`agent-handoff.md`](agent-handoff.md)。
